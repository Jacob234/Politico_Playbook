# Handoff: v0.2 Multi-Newsletter Ingestion Redesign

## Session Overview

**Date**: 2026-05-05
**Duration**: One long session (initial scope discussion → full implementation → cleanup)
**Primary Goal**: Redesign the Politico Playbook extraction tool from a single-source POC into a multi-newsletter pipeline covering ~27 POLITICO newsletters across the Politico landscape.

This is the **first** handoff in this project — no parent handoffs exist yet.

## What Was Accomplished

A complete v0.1 → v0.2 architectural redesign across **11 commits**, ending in a clean, modern Python package layout:

1. **Discovery** — Used Claude.ai Gmail MCP tools to inventory the user's `politicollector@gmail.com` mailbox: identified 27+ distinct newsletters, mailbox starts ~Feb 2025 (~15 months of history), estimated 8K–15K total messages. Sender-slug pattern (`<slug>@email.politico.com`) identified as the clean newsletter-ID key.
2. **Sampling** — Pulled full-content samples from 5 structurally diverse newsletters (`politicoplaybook`, `westwingplaybook`, `newyorkplaybook`, `pulse`, `weeklyscore`, `newsletter_politicopro`) to map out section header conventions. Discovered that flagship Playbook uses ALL CAPS headers while West Wing/Pulse/Pro use Title Case, and that the same semantic concept appears under different labels (e.g., `TRANSITIONS` ≡ `Names in the News` ≡ inline `WHITE HOUSE SHAKE-UP` callouts).
3. **Design doc** — Wrote `docs/superpowers/specs/2026-05-05-multi-newsletter-ingestion-design.md` capturing all decisions before any code was written.
4. **Stage 1: Ingestion layer**
   - `ingestion/gmail_client.py` — Gmail API + OAuth (read-only scope), two-phase fetch (cheap ID listing → on-demand full message), exponential backoff on 429/5xx.
   - `ingestion/raw_store.py` — SQLite store keyed on `gmail_message_id` (idempotent upsert), incremental queries via `MAX(received_at) WHERE newsletter_slug=?`.
   - `ingestion/newsletter_registry.py` — YAML-driven, sender-slug-keyed (with synthetic slug `newsletter_politicopro` for the multi-vertical Pro sender). 27 newsletters in `config/newsletters.yaml`.
   - `ingestion/parser_base.py` — Sponsor-block stripping (`BEGIN-REGION`/`END-REGION`), section detection driven by `section_taxonomy.yaml`, case+colon-insensitive header matching.
   - `ingestion/runner.py` — Single CLI: `backfill | incremental | inventory | extract`.
5. **Section taxonomy** — Built `config/section_taxonomy.yaml` from sampling 5 newsletter types. Three-layer precedence: `by_newsletter[slug][header]` → `shared[header]` → `skip_headers`. Resolves cross-newsletter label variants to a small set of types (`personnel_change`, `social_graph`, `lead_story`, `news_brief`, `state_news`, `campaign_news`, `financial`, `links_only`, `ignore`).
6. **Stage 2: Model-agnostic extraction**
   - `llm/openrouter_client.py` — OpenAI SDK pointed at `https://openrouter.ai/api/v1`. Pass-through prompt caching for Anthropic-routed models via `extra_body`. JSON-schema structured output.
   - `config/extraction_prompts.yaml` — Section-type-specific prompts and JSON schemas with `inherit:` semantics (news_brief/state_news/financial inherit from unclassified; personnel_change/social_graph/lead_story/campaign_news have specialized schemas).
   - `processing/section_extractor.py` — Bridges raw_store + parser + LLM. Persists results to `extractions` table keyed on `(gmail_message_id, section_index, model_id)` for idempotency under model swaps.
7. **Cleanup** (5 commits) — Removed 70+ files (~24,800 lines):
   - v0.1 stale data (raw HTMLs, structured JSONs, claude_enhanced outputs, build cruft)
   - v0.1 deprecated code (IMAP `email_client.py`, `claude_nlp_processor.py`, `pipeline_orchestrator.py`, `nlp_processor.py`, `html_to_json.py`, etc.)
   - v0.1 docs and notebook (`PIPELINE_README.md`, `claude_nlp_*.md`, `claude_nlp_testing.ipynb`)
   - Broken v0.1 tests that imported deleted modules
   - Stale `playbook-poc-plan.md`
8. **Flattened `src/`** — `politico_playbook/src/<x>/` → `politico_playbook/<x>/`. All imports updated, path-finding code adjusted (`parents[3]` → `parents[2]` in runner, `parents[2]` → `parents[1]` in parser_base). Used `git mv` to preserve per-file history.
9. **Documentation** — Rewrote `CLAUDE.md` and `README.md` to reflect the v0.2 architecture, new CLI invocations, OAuth/OpenRouter setup, and the migration story.
10. **Tag `v0.1-poc-single-source`** — Created at the pre-redesign state. Recovers any v0.1 file with `git checkout v0.1-poc-single-source -- <path>` or restores the entire tree with `git checkout v0.1-poc-single-source`.

## Key Decisions & Context

### Decision 1: "Archive via tag, not folder copy"
**Context**: User asked "should we make a copy for archival purposes and then start fresh?"
**Decision**: Tag with `v0.1-poc-single-source`, redesign Stage 1 cleanly, but **keep Stages 2–4 conceptually untouched** (they're source-agnostic; only the model-call layer changed).
**Rationale**: A git tag preserves recoverability with zero working-tree clutter. Stages 2–4 (~1,800 LOC) contain real domain logic — schemas, normalization rules, prompts — that would be expensive to rewrite without justification.
**Alternatives Considered**: Wholesale rewrite (rejected — would lose domain knowledge); literal folder copy (rejected — clutters tree).

### Decision 2: "Gmail API + OAuth" (replacing IMAP App Password)
**Context**: Existing `email_client.py` used IMAP with hardcoded credentials and a 4-day Aug 2025 date window.
**Decision**: Migrate to Gmail API via `google-api-python-client` with OAuth 2.0 Desktop client. Token cached at `~/.config/politico-pipeline/token.json`.
**Rationale**: App Passwords are on Google's slow-deprecation track; Gmail API offers batch fetch (~10x faster), proper threading, page tokens, label filtering, and official long-term support. One-time OAuth dance is acceptable for a single-developer tool.
**Alternatives Considered**: Stay on IMAP (simpler short-term, dies long-term); use Google Takeout mbox for bulk backfill (deferred as bolt-on if Gmail API rate limits become a problem).

### Decision 3: "OpenRouter for model-agnostic Stage 2" (user-driven)
**Context**: User explicitly requested model-agnostic via OpenRouter rather than direct Anthropic SDK, after I laid out four upgrades (Gmail API, SQLite, Takeout, Batches+caching).
**Decision**: OpenAI SDK pointed at `https://openrouter.ai/api/v1`. `MODEL_ID` env var selects model. Anthropic prompt caching passed through via `extra_body`.
**Rationale**: Cross-provider optionality is the win. User accepted the trade-off that **OpenRouter does not proxy Anthropic's Message Batches API** — net cost reduction is ~5x (caching only) instead of ~10x (caching + batches). Decision was "A: pure OpenRouter, accept 5x" rather than "B: hybrid with optional direct Anthropic batch path."
**User-chosen default model**: `tencent/hy3-preview:free` for plumbing/dev (rate-limited free tier — verify exact slug at https://openrouter.ai/models before real run; expected swap to a paid model like `anthropic/claude-haiku-4-5` for production-volume backfill).

### Decision 4: "Section-aware extraction with YAML taxonomy"
**Context**: After sampling 5 newsletters, discovered headers are wildly inconsistent across newsletters but semantically reducible to a small type set.
**Decision**: Three-layer YAML taxonomy — `by_newsletter[slug][header]` (per-newsletter overrides) → `shared[header]` (cross-newsletter) → `skip_headers` (recognize but don't extract). Stage 2 sends each non-skip section to the LLM separately with section-type metadata, using a section-typed prompt.
**Rationale**: Section-typed prompts dramatically improve extraction quality vs whole-body blob. Personnel-change sections become structured `(name, prior_role, new_role)` extractions; social-graph sections become structured name lists. Editing the YAML doesn't require touching Python.
**Alternatives Considered**: Single whole-body prompt (rejected — wastes section-type priors); per-newsletter Python parsers (rejected — premature; one shared parser handles ~95% of cases via the registry's `parser:` field for overrides).

### Decision 5: "Flatten `src/`" (Phase 3 cleanup)
**Context**: User chose option C: full cleanup including the `src/` flatten reorder.
**Decision**: Move `politico_playbook/src/<x>/` → `politico_playbook/<x>/`. Update imports (only 2 files had cross-package imports). Update `parents[N]` path-finders.
**Rationale**: `src/` is a fossil from when projects often used it to separate Python source from build artifacts; modern packaging handles that. Flattening makes imports terser, aligns with PEP 518, and makes the package directly `pip install -e .`-able.
**Cost**: 17 file moves (preserved as renames in git history via `git mv`), 28 lines changed.

### Decision 6: "Idempotency at multiple levels"
**Context**: A backfill of 8K–15K messages will inevitably get interrupted. Re-running needs to be safe.
**Decision**: Two-level idempotency:
- **Ingestion**: `gmail_message_id` PRIMARY KEY in `raw_emails` — re-running `backfill` is a no-op for already-stored messages.
- **Extraction**: `(gmail_message_id, section_index, model_id)` UNIQUE in `extractions` — re-running `extract` for the same model overwrites in place. Switching `MODEL_ID` produces a fresh row, useful for A/B comparison across providers.
**Rationale**: This makes failure handling trivial: just re-run. Also makes the system observable — `processing_status` column shows what's pending vs. parsed vs. failed.

- `RAW_EMAILS_DB` (default: `data/raw_emails.db`)

### Known Caveats
- Free-tier OpenRouter models (`:free` suffix) have aggressive rate limits — fine for dev, infeasible for full backfill.
- Gmail API quota: ~250 quota units/sec; `messages.get` costs ~5 units; ~50 messages/sec sustained throughput. 8K-15K backfill ≈ 3-5 minutes.
- OpenRouter does NOT proxy Anthropic's Message Batches API. If Batches discount becomes critical, would need a hybrid path (deferred decision).

### Performance Considerations
- Two-phase fetch in `gmail_client.py` (list IDs → fetch full) means we can check `raw_emails` for existing message_id BEFORE paying the cost of fetching the full message. Critical for re-run efficiency.
- SQLite is more than enough for this scale (15K rows × ~15KB each ≈ 225MB DB). No need for Postgres yet.
- Prompt caching gains depend heavily on system prompt being identical across requests. The `extraction_prompts.yaml` system messages ARE identical per section_type, so cache hit rate should be ≥90% within a section type.
